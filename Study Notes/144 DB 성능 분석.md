## 📝 핵심 개념 요약

- 실행계획은 DB가 SQL을 실행하기 위해 선택한 **최적의 경로 지도**
- 같은 쿼리라도 **여러 실행계획 후보 중 Cost가 가장 낮은 것**을 선택
- 핵심 관찰 포인트는 **Scan 방식 / Cost / Rows**
- 인덱스 유무와 조건 범위에 따라
    
    `Seq Scan → Index Scan → Index Only Scan`으로 진화
    
- **조건 범위가 좁을수록 인덱스 효과는 폭발적으로 증가**

## 📊 핵심 요약 표

| 요소 | 의미 | 체크 포인트 |
| --- | --- | --- |
| Scan 방식 | 데이터를 어떻게 읽는지 | Seq Scan vs Index Scan |
| Cost | DB가 예상한 작업량 | 상대값, 낮을수록 좋음 |
| Rows | 실제로 건드린 행 수 | 많을수록 느림 |
| Filter | 읽고 나서 거름 | 인덱스 못 쓴 신호 |
| Index Cond | 처음부터 범위 지정 | 인덱스 제대로 사용 |

### 💻 실습 내용 정리

- `EXPLAIN SELECT ...`로 쿼리 실행계획 확인
- 인덱스 미적용 시 `Parallel Seq Scan` 발생
- 조건 필터(`Filter`)로 인해 100만+ row 전체 스캔
- `age` 컬럼에 인덱스 생성 후 `Index Only Scan` 확인
- `Filter` → `Index Cond`로 변경되며 Cost 급감
- 조건 범위를 좁히자 Cost가 **약 1/13 수준으로 감소**

### ❗ 헷갈렸던 점 / 문제 해결:

- ❓ *Cost가 시간(ms)인가?*
    
    → ❌ 아님. **DB 내부의 상대적 작업량 지표**
    
- ❓ *왜 인덱스가 있는데도 느릴까?*
    
    → 조건 범위가 너무 넓으면 인덱스도 비효율적
    
- ❓ *Index Only Scan이 뜨는 이유는?*
    
    → 필요한 컬럼이 전부 인덱스에 포함되어 테이블 접근이 필요 없기 때문
    

### 💡 느낀 점 / 배운 점:

- 쿼리는 “어떻게 실행되느냐”가 성능의 전부
- 인덱스 유무보다 **실행계획을 읽을 줄 아는 능력**이 더 중요
- 성능 튜닝은 감이 아니라 **EXPLAIN 결과 기반의 판단**
- Rows 수를 줄이는 것이 성능 개선의 핵심이라는 걸 체감함

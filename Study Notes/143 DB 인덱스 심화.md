## 📝 핵심 개념 요약

- 인덱스는 **조회 성능을 비약적으로 향상**시키지만, 그만큼 **쓰기 작업 비용**이 발생한다.
- Full Scan은 데이터가 많아질수록 선형적으로 느려진다.
- Index Scan은 정렬된 구조 덕분에 **필요한 데이터 위치로 바로 점프**한다.
- 인덱스는 무조건 많이 만드는 것이 아니라, **자주 조회되고 변별력이 높은 컬럼**에만 적용해야 한다.

## 📊 핵심 요약 표

| 구분 | Full Scan | Index Scan |
| --- | --- | --- |
| 탐색 방식 | 모든 행을 처음부터 끝까지 검사 | 인덱스를 통해 위치를 바로 탐색 |
| 속도 | 데이터 양에 비례해 느려짐 | 데이터가 많아도 매우 빠름 |
| 사용 조건 | 인덱스 없음 | 인덱스 존재 |
| 비유 | 책을 처음부터 끝까지 넘김 | 찾아보기 보고 바로 페이지 이동 |

### 💻 실습 내용 정리

- `name` 컬럼에 인덱스가 없는 경우, 특정 이름 조회 시 전체 레코드를 끝까지 탐색해야 함
- `name` 컬럼에 인덱스가 있는 경우, 정렬된 인덱스를 통해 빠르게 대상 레코드 탐색
- INSERT 시 메인 테이블 + 인덱스 구조를 **동시에 갱신해야 함**을 확인
- 자주 사용하는 `WHERE email = ?` 같은 조건은 인덱스 대상
- 거의 조회하지 않는 컬럼이나 중복도가 높은 컬럼은 인덱스 비효율적

### ❗ 헷갈렸던 점 / 문제 해결:

- ❓ *“인덱스는 많을수록 좋은 거 아닌가?”*
    
    → ❌ 아님. 인덱스가 많아질수록 **INSERT / UPDATE / DELETE 성능 저하**
    
- ❓ *“성별, Y/N 컬럼에도 인덱스 걸면 빠르지 않나?”*
    
    → ❌ 결과 집합이 너무 커서 인덱스 효과가 거의 없음
    

### 💡 느낀 점 / 배운 점:

- DB 성능 문제는 대부분 **쿼리 문제가 아니라 설계 문제**
- 인덱스는 “조회 최적화 도구”이지 “만능 가속기”가 아님
- **조회 빈도 + 중복도** 기준으로 인덱스를 판단해야 한다
- 실무에서는 “느린 쿼리 발견 → 인덱스 추가” 흐름이 중요하다는 걸 이해함

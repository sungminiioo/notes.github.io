## 📝 핵심 개념 요약

### 1️⃣ 테스트 이름의 핵심 원칙

- **구현(How)이 아니라 의도(What & Why)를 설명**
- 비개발자도 이해할 수 있는 수준의 이름
- 비즈니스 규칙과 직접 연결된 표현 사용
    
    👉 테스트 이름 자체가 **문서 역할**을 하도록 작성
    

---

### 2️⃣ describe / test 역할 구분

- **describe**: 구조화 & 기능 그룹핑
- **test**: 실제 시나리오와 결과 표현

```
describe → “무엇에 대한 테스트 묶음인가?”
test     → “이 상황에서 어떤 일이 일어나야 하는가?”
```

---

### 3️⃣ 테스트 레벨 구분

| 테스트 대상 | 테스트 레벨 | 도구 |
| --- | --- | --- |
| 미들웨어 / 순수 함수 | 유닛 테스트 | jest |
| API 엔드포인트 | 통합 테스트 | supertest |
| DB 연동 로직 | 통합 테스트 | 실제 테스트 DB |

---

### 4️⃣ 모킹(Mock)의 기준

- **부작용(Side Effect)이 있는 것만 모킹**
- 내부 계산 로직은 모킹 ❌
- 외부 시스템 연동은 모킹 ✅

## 📊 핵심 요약 표

| 구분 | 핵심 내용 |
| --- | --- |
| 테스트 이름 | 구현보다 **비즈니스 의도 중심** |
| describe | 기능/도메인 단위 그룹핑 |
| test | 사용자 시나리오 기반 |
| 모킹 대상 | 외부 API, 이메일, 파일, 클라우드 |
| DB | 테스트 DB가 있으면 실제 사용 |
| 장점 | 리팩토링에 강한 테스트 |

### 💻 실습 내용 정리

### ✔️ 테스트 이름 짓기 개선 연습

### ❌ 구현 중심 테스트

```jsx
test('User.create()가 호출된다',() => {})
```

### ✅ 의도 중심 테스트

```jsx
test('유효한 정보로 회원가입하면 새 계정이 생성된다',() => {})
```

---

### ✔️ 미들웨어 유닛 테스트

- JWT 검증 로직 모킹
- req / res / next 직접 생성
- 인증 성공 vs 실패 시나리오 분리

---

### ✔️ API 통합 테스트 (supertest)

- 실제 테스트 DB 사용
- 이메일, 결제, S3 같은 외부 서비스만 모킹
- API 응답 + DB 상태 **동시에 검증**

---

### ✔️ 버그 리포트를 단위 테스트로 분해

- 하나의 버그 → 여러 개의 작은 테스트
- 로직 단위로 책임 분리

```jsx
test('상품 제거 시 할인 금액이 재계산된다',() => {})
test('마지막 상품 제거 시 쿠폰 할인이 0원으로 초기화된다',() => {})
```

### ❗ 헷갈렸던 점 / 문제 해결:

### ❓ 언제 모킹해야 할지 헷갈림

- 👉 **외부 영향이 있는지 기준으로 판단**
- DB는 테스트 전용이라면 모킹 ❌

### ❓ describe에 함수명을 써도 되는지?

- 👉 전혀 문제 없음
- 실무에서는 **기능명 + 함수명 혼합 방식**이 가장 흔함

### 💡 느낀 점 / 배운 점:

- 테스트 이름만 봐도 **시스템 동작이 이해되면 좋은 테스트**
- 구현 디테일에 묶인 테스트는 리팩토링에 약함
- 테스트는 “검증 코드”이자 **팀을 위한 문서**
- 버그를 테스트로 남기면 같은 실수를 반복하지 않게 됨

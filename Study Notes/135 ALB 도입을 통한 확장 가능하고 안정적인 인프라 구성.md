## 📝 핵심 개념 요약

- *ALB(Application Load Balancer)**는 HTTP/HTTPS 트래픽을 처리하는 AWS 관리형 로드 밸런서
- ALB 도입 시 **외부 트래픽은 ALB만 노출**, EC2는 **프라이빗 서브넷**에 배치 가능
- EC2는 퍼블릭 IP가 필요 없어지고, **보안 그룹으로 ALB만 허용**하는 구조 설계 가능
- AWS Shield 기본 탑재로 **DDoS 및 비정상 트래픽 자동 방어**
- Target Group, Listener, Rule 기반으로 **유연한 트래픽 분산** 가능
- 현재 구조는 **HTTP만 지원** → HTTPS 적용을 위해 도메인 + ACM 필요

### 💻 실습 내용 정리

### 1️⃣ ALB 아키텍처 구조 변화

**기존 구조**

```bash
Client →EC2 (Public IP)
```

**ALB 도입 후**

```
Client → ALB (Public Subnet)
             ↓
         EC2 (Private Subnet)
```

---

### 2️⃣ ALB 생성 실습 흐름

1. **EC2 콘솔 → 로드 밸런서 → ALB 생성**
2. **모든 가용영역(AZ) 선택**
    - ALB는 특정 AZ에 귀속되지 않는 AWS 관리형 서비스
3. **보안 그룹 생성**
    - 인바운드: HTTP(80), HTTPS(443) → Anywhere-IPv4
4. **ALB에 새 보안 그룹 연결**
5. **Target Group 생성**
    - 대상: EC2 인스턴스
    - 포트: 80
6. **헬스 체크 설정**
    - 경로: `/health`
    - 서버 응답 코드 200 확인

```jsx
app.get("/health",(req, res) => {
  res.send("Health Check Success");
});
```

1. **리스너 설정**
    - 포트 80 → Target Group 연결
2. **로드 밸런서 생성 완료**
3. **ALB DNS 주소로 Rest Client 테스트**

### ❗ 헷갈렸던 점 / 문제 해결:

### ❓ 왜 ALB가 있으면 EC2를 Private Subnet에 둘 수 있을까?

- 외부 요청은 **ALB가 대신 수신**
- EC2는 ALB에서 오는 트래픽만 허용
- 퍼블릭 IP, IGW 필요 없음
- 공격 표면이 **EC2 → ALB로 이동**

### ❗ 헬스 체크 실패 문제

- `/health` 엔드포인트가 서버에 없으면 대상 그룹에서 **Unhealthy**
- 해결: 서버에 GET `/health` API 추가

### 💡 느낀 점 / 배운 점:

- **“보안은 숨기는 것부터 시작”** 이라는 개념을 이해함
- ALB는 단순한 트래픽 분산이 아니라 **보안·확장성·운영 안정성의 핵심**
- 실제 서비스에서는 **ALB + HTTPS + 도메인**이 기본 구조라는 점을 체감
- 인프라 설계에서 “왜 이렇게 구성하는가”가 훨씬 중요하다는 걸 느낌

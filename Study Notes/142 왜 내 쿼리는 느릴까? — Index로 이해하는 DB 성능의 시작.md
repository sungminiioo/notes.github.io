## 📝 핵심 개념 요약

### 왜 쿼리가 느려질까?

- 데이터가 많아질수록 **모든 데이터를 하나씩 확인하는 방식**은 한계가 있음
- 문제의 본질은 **데이터 양이 아니라 “찾는 방법”**
- 대부분의 성능 문제는 **Index 부재 또는 잘못된 사용**에서 발생

---

### 🔍 Full Scan (전수 조사)

- 테이블의 **모든 행을 하나씩 검사**
- 데이터가 적을 땐 문제 없음
- 데이터가 많아질수록 **선형적으로 성능 저하**
- CPU + 디스크 I/O 부담 큼

---

### ⚡ Index Scan (색인 활용)

- 미리 정렬된 **인덱스 구조**를 통해 빠르게 위치 탐색
- 필요한 데이터 위치로 **즉시 점프**
- 데이터 수가 커져도 성능 저하가 적음

---

### 📚 인덱스(Index)의 본질

- 책 뒤의 **‘찾아보기’**와 동일한 개념
- 실제 데이터와 분리된 **별도의 자료 구조**
- 특정 컬럼 기준으로 **정렬된 상태** 유지
- 빠른 검색 → 실제 데이터 접근

## 📊 핵심 요약 표

| 구분 | Full Scan | Index Scan |
| --- | --- | --- |
| 탐색 방식 | 모든 데이터 순차 탐색 | 정렬된 인덱스 기반 탐색 |
| 속도 | 데이터가 많을수록 느림 | 데이터가 많아도 빠름 |
| 리소스 | CPU, 디스크 사용량 큼 | 리소스 효율적 |
| 비유 | 책을 처음부터 끝까지 읽기 | 찾아보기로 바로 찾기 |
| 사용 조건 | 인덱스 없음 | 인덱스 존재 |

### 💻 실습 내용 정리

- 아직 직접 SQL 실습은 없었으나,
    - **왜 인덱스가 필요한지에 대한 개념적 기반**을 확실히 이해함
- 이후 실습 예정:
    - `EXPLAIN`으로 Full Scan / Index Scan 확인
    - 인덱스 생성 전·후 쿼리 속도 비교

### ❗ 헷갈렸던 점 / 문제 해결:

❓ “데이터가 많아서 느린 줄 알았는데 왜 인덱스가 없으면 더 느릴까?”

- 👉 문제는 **양(quantity)** 이 아니라 **경로(path)**
- 👉 인덱스가 없으면 DB는 선택지가 없어 Full Scan을 강제함

### 💡 느낀 점 / 배운 점:

- 성능 문제는 하드웨어보다 **설계 문제**인 경우가 많다
- 인덱스는 “옵션”이 아니라 **대용량 서비스의 필수 요소**
- 앞으로 쿼리가 느리면
    
    👉 **“인덱스가 있는가?”부터 의심해야겠다**
